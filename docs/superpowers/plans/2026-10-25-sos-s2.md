# SOS S2 구현 계획 (B 영역)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 이 계획은 S1(나라장터 4종 → 사업 리드)을 넓혀 네 가지를 더한다.
- 낙찰·계약 정보: 리드 단계를 **낙찰/계약**까지 잇고 **경쟁사(낙찰자)** 를 보여 준다.
- 재발주 예측: 계약 종료일로 **재발주 예측 리드(`predicted`)** 를 만든다.
- 채용 기관 시그널: 고용24·사람인 채용을 **기관 시그널**로 받는다. 점수에 더하고, 사업 리드가 없는 기관은 **사업 미확인 리드(`org_only`)** 로 만든다.
- 사람 작업: **기관 확인 필요** 화면과 **영업사원 수동 리드 등록**.

**Architecture:** S1의 "실행(run) = 60초 안 단계들" 구조를 그대로 쓴다.
- 새 출처는 수집기(순수 정규화 + server-only fetch)로 추가한다. 실행 계획 `planRun` 에는 단계로 끼운다.
- 낙찰·계약 원문은 14일 보관 원본(`sos_raw_items`)에 넣는다. 키워드에 맞은 건은 추가로 3년 보관 공용 이력(`sos_org_history`)에 남긴다. 경쟁사 이력과 재발주 예측은 이 이력 표에서 계산한다.
- 기관 연결은 순수 함수 `resolveOrg` 가 맡는다. 확신이 없으면 공용 대기열 `sos_org_reviews` 에 넣고 사람이 고른다.

**Tech Stack:** Next.js 16 (App Router, `cacheComponents`), Supabase(Postgres + RLS), Vitest, TypeScript. 새 npm 의존성은 없다.

**Spec:** `docs/superpowers/specs/2026-10-20-sos-design.md` (PR #6 브랜치 `b/sos-design`. 머지 전이면 `git show origin/b/sos-design:docs/superpowers/specs/2026-10-20-sos-design.md`). S2 범위는 §10 표이고, 함께 볼 곳은 §2.1 출처, §3.3 분석, §4 데이터, §5.1 탭, §6.1·6.3 A 연동, §8 테스트다.

## 1. 확정한 결정 (DJ, 2026-10-25)

- **재발주 예정월** = 계약 종료월 − `reorder_lead_months`(부문 설정, 기본 **3**). 예정월 **6개월 전부터** 목록에 보인다.
- **계약 이력:** 부문과 무관하게 공용으로 **한 번만 지난 12개월치를 백필**한다. 주 단위로 받고, 어느 부문 키워드에든 맞은 계약만 이력에 저장한다. 그 뒤로는 실행 범위만 받는다.
- **채용 잡음:** API의 **직무 분류**(인프라·시스템·네트워크·보안·DBA)로 먼저 거르고, 그 안에서 `sources` 에 `jobs` 가 켜진 키워드로 맞춘다.
- **채용만 있고 사업 리드가 없는 기관** → **사업 미확인 리드**(`org_only`, 기관당 1장)를 만든다. 사업 리드가 있으면 점수 가산만 한다.
- **예측 리드 ↔ 실제 리드:** 자동으로 합치지 않는다. 같은 기관 + 연도 뗀 사업명이 같으면 "같은 사업일 수 있음 → [합치기]" 를 띄운다. 수동 리드도 같은 규칙을 쓴다.
- **경쟁사:** 리드 카드(낙찰자·낙찰금액) + **기관별 보기**의 "이 기관 지난 낙찰·계약 업체"까지. 경쟁사 집계 화면은 만들지 않는다.
- **DealSignals(§6.3):** S2 마지막 PR로 넣는다.
- [제안] 기관 연결 결정(별칭 추가·새 기관)은 공용 `sos_orgs` 에 반영되므로 **모든 부문에 적용**된다. 부문 멤버 누구나 할 수 있다.
- [제안] 겹침 점수 `orgSignals90d` 는 S1의 "같은 기관 다른 리드 수"에 **최근 90일 기관 시그널 원본 수(중복 없이)** 를 더한다. 상한 +4는 그대로다.

## Global Constraints

- 영역: B 파일(`src/app/sos/**`, `src/features/sos/**`, `supabase/migrations/*_b_*.sql`)만 고친다. 공용(`.env.example`, `src/shared/**`)은 별도 작은 PR로 하고 A 리뷰를 받는다. A 영역(`src/features/deals/**` 등)은 수정하지 않는다.
- 마이그레이션은 `npx supabase migration new b_<설명>` 으로 만들고 **코드보다 먼저 별도 PR**로 낸다. 이미 머지된 마이그레이션 파일은 수정하지 않는다. 운영·개발 DB가 같은 프로젝트(`gofmfcupfoirfcyhumtl`)라 **머지 즉시 운영에 적용된다.**
- 새 테이블은 `sos_` 접두사 + RLS를 쓴다. 권한은 `anon`·`authenticated` 를 전부 회수한 뒤 필요한 것만 다시 주고, `service_role` 에는 전부 준다 (`20261022100000_b_sos_core.sql` 관례).
- 비밀값 `SARAMIN_ACCESS_KEY`, `WORK24_AUTH_KEY` 는 `src/features/sos/server/env.ts`(server-only)에서만 읽는다. `NEXT_PUBLIC_` 금지. 키·키가 든 URL은 로그·오류 메시지·픽스처에 남기지 않는다.
- 관리자 클라이언트(secret key) 경로의 `team_id` 는 `requireSosTeam()` 결과만 쓰고, 모든 쿼리에 `team_id` 조건을 명시한다 (설계서 §7).
- 사업 생성은 `createDealFromLead()` 로만 한다. `procurement` 는 `"bid" | "negotiated"` 다.
- 한 단계 = 서버 호출 한 번 **60초 안**이다. 외부 호출은 `withRetry`(`collectors/retry.ts`)로 하고 한 쪽 예산은 40초다.
- 원본 저장 전 개인정보를 지운다. 조달은 기존 `stripPersonal` 을 쓰고, 채용은 담당자 이름·연락처·이메일 필드를 지운다.
- 서버에서 `new Date()` 를 쓰는 화면 코드는 `await connection()` 뒤에 둔다. 세션을 읽는 컴포넌트는 `<Suspense>` 안에 둔다.
- CI에서 실제 API를 호출하지 않는다. 수집기는 녹화한 JSON(또는 XML) 픽스처로 검증한다.
- 로컬 테스트 데이터는 `[TEST]` 접두사로 만들고 확인 뒤 지운다.
- push 전 `npm run check` 통과. 브랜치 `b/<기능>`, 작업 시작과 함께 Draft PR. 리뷰 댓글 머리에 `[B-Claude]`.

## Review Focus

1. **수동 리드가 나중에 수집으로 다시 들어오는 경우** — 같은 기관·같은 사업명이면 카드 두 장이 조용히 쌓이지 않고 "같은 사업일 수 있음"이 떠야 한다 → Task 12 `likelySameBusiness` 테스트에 수동 리드 케이스.
2. **계약기간 표기가 제각각인 경우**("2025.01.01~2025.12.31", "20250101-20251231", "착수일로부터 365일", 빈 값) → 못 읽으면 예측하지 않는다(null). 틀린 예정월을 지어내지 않는다 → Task 9 `parseContractPeriod` 테스트.
3. **같은 이름(또는 별칭)이 여러 기관에 걸리는 경우** → 아무 기관에도 붙이지 않고 확인 대기열로 보낸다 → Task 13 `resolveOrg` 테스트.
4. **채용 키가 아직 없는 경우**(사람인 승인 전) → 그 출처는 "건너뜀(키 없음)"으로 표시한다. 실행은 `partial` 이 되지 않고 조달 수집은 그대로 돈다 → Task 15 `planRun` 테스트.
5. **백필이 중간에 끊기는 경우**(한도 초과·탭 닫힘) → 다음 실행이 받지 못한 주만 이어 받는다. 이미 받은 주는 다시 부르지 않는다 → Task 10 `missingBackfillWeeks` 테스트.
