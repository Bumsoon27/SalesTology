# SOS S2 구현 계획 — 유지보수 계약 갱신 예측 (B 영역)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 공공기관의 유지보수 계약이 **끝나기 3개월 전**에 "갱신 예측" 리드를 띄운다. 카드는 교체 제안 근거로 **현재 업체·계약금액·종료일(D-n)** 을 보여 준다.

**Architecture:** S1의 "실행(run) = 60초 안 단계들" 구조에 단계 두 개를 더한다.
- **계약 수집** 단계는 나라장터 계약정보를 주 단위로 받는다. 어느 부문 키워드에든 맞은 계약만 공용 표 `sos_contracts` 에 3년 보관한다.
  - 최근 15개월 중 아직 받지 않은 주만 받는다. 첫 실행이 사실상 백필이 된다.
- **갱신 예측** 단계는 `sos_contracts` 에서 부문 키워드 + 유지보수 조건에 맞는 계약을 고른다. 종료일이 `reorder_lead_months`(기본 3) 안이면 `predicted` 리드를 upsert한다.
- 다음 해 실제 사전규격·입찰공고가 들어오면 analyze-save 가 같은 기관 + 같은 사업명(연도 무시) 예측 리드를 찾는다. 하나뿐이면 새 카드 대신 그 리드를 이어 단계를 올린다.

**Tech Stack:** Next.js 16 (App Router, `cacheComponents`), Supabase(Postgres + RLS), Vitest, TypeScript. 새 npm 의존성·새 비밀값은 없다(기존 `DATA_GO_KR_SERVICE_KEY` 사용).

**Spec:** `docs/superpowers/specs/2026-10-20-sos-design.md` (PR #6 브랜치 `b/sos-design`. 머지 전이면 `git show origin/b/sos-design:docs/superpowers/specs/2026-10-20-sos-design.md`). 관련 절은 §2.1(계약정보), §3.3(묶기·점수·갱신 규칙), §4.2(`sos_leads.kind = predicted`), §4.3(보관), §6.1(전환), §7·§8이다. 범위는 아래 §1의 DJ 결정(2026-10-28)으로 §10 S2 행을 **좁힌 것**이다.

## 1. 확정한 결정 (DJ, 2026-10-28)

- S2 목표는 **유지보수 계약 갱신 예측 하나**다.
- 예측 리드는 **종료일이 3개월 안**일 때 만든다. 3개월은 부문 설정 `reorder_lead_months` 로 조정할 수 있다.
- 예측 리드는 S1과 **같은 목록**에 '갱신 예측' 표시로 함께 나온다. 점수·담당·메모·보류/관심 없음·[사업으로 전환]은 그대로 쓴다.
- 카드 핵심 숫자는 **현재 업체 · 계약금액 · 종료일 D-n · 일치 키워드**다.
- 경쟁사 정보는 이 "현재 업체" 표시로만 쓴다.
- 대부분 연간 계약이므로 **약 9~15개월 전에 체결된 계약**을 보면 대부분 잡힌다. 그래서 계약은 최근 15개월을 받아 둔다.
- [제안] 계약 원문은 14일 보관 원본(`sos_raw_items`)에 넣지 않는다. 예측 근거는 1년 넘게 필요하므로 공용 `sos_contracts` 에 **키워드에 맞은 계약만** 3년 보관한다.
- [제안] 유지보수 조건은 저장할 때가 아니라 **예측할 때** 건다. Q1 답이 바뀌어도 다시 받지 않아도 된다.

## Review Focus

1. **계약기간 표기가 제각각인 경우**("2025.01.01~2025.12.31", "20250101-20251231", "착수일로부터 365일", 빈 값) → 못 읽으면 예측하지 않는다(null). 날짜를 지어내지 않는다 → Task 3 `parseContractPeriod` 테스트.
2. **같은 계약이 변경계약(차수)으로 여러 번 오는 경우** → 마지막 차수의 종료일·금액 하나만 남고 리드도 하나다 → Task 3 `latestContracts` 테스트.
3. **이어 붙일 예측 리드 후보가 둘 이상인 경우**(같은 기관에 비슷한 유지보수 계약 둘) → 아무 데도 잇지 않고 새 리드를 만든다 → Task 7 `findPredictedMatch` 테스트.
4. **수집이 중간에 끊기는 경우**(한도 초과·탭 닫힘) → 다음 실행이 받지 못한 주만 받고 이미 받은 주는 다시 부르지 않는다. 이번 주(끝나지 않은 주)는 매번 다시 받는다 → Task 4 `missingContractWeeks` 테스트.
5. **사람이 손댄 예측 리드가 다시 분석되는 경우** → 상태·담당·메모를 덮어쓰지 않는다. 관심 없음이면 숨긴 채 근거만 갱신한다 → Task 5 테스트(`applyLeadUpdate` 재사용 확인).
