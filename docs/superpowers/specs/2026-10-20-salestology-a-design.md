## 0. 프로젝트 구성과 역할 분담

SalesTology는 한 저장소, 한 웹 앱 안에 두 개의 독립 기능 영역을 둔다. 로그인과 회사·사용자 기본 데이터는 공유한다.

| 영역 | 담당 | 범위 |
|---|---|---|
| **A. SalesTology 코어** | SB | 로그인·가입, 메인 대시보드, 토폴로지뷰, 알림(티커·종), 사업·회사 기본 데이터 |
| **B. SOS** (Signal-based Outbound Sales) | DJ | 시그널 기반 아웃바운드 세일즈. **이 문서 범위 밖**, DJ가 별도 설계서 작성 |

이 문서는 **A 영역**만 다룬다. B와의 경계와 공동 작업 규칙은 §11에 둔다.

## 1. 목적과 성공 기준

### 1.1 목적
영업팀이 진행 중인 사업, 고객사, 관계사(SI·매입처)를 **'나'를 중심으로 한 방사형 토폴로지** 로 한눈에 보고, 견적요청 회신·발주·납품·세금계산서 같은 **놓치기 쉬운 업무**와 위험 신호를 색으로 즉시 알아채 바로 처리하게 한다. 이 화면이 서비스의 **메인 대시보드**다.

### 1.2 성공 기준
1. 로그인하면 내가 담당한 고객사·사업이 방사형 맵으로 표시된다.
2. 노드 색상이 규칙(§4)대로 자동 계산되고, 날짜가 지나면 별도 조작 없이 바뀐다.
3. 확인이 필요한 업무가 맵에 드러나고, 그 업무로 **바로 이동해 처리**할 수 있다.
4. 맵은 궤도 위에서 부드럽게 움직이되, 노드가 겹치거나 가지가 섞이지 않는다.
5. 상단 티커와 종 알림이 급한 일을 계속 보여주고, 클릭하면 해당 노드로 이동한다.
6. 색을 구분하지 못해도 상태명·사유·건수로 상태를 알 수 있다.
7. 다른 부문의 데이터는 보이지 않는다.

### 1.3 이번 단계(A1)에 포함
- 부문 코드 기반 가입, ID/비밀번호 로그인, 최초 관리자 계정, 최소 관리자 화면
- 핵심 데이터: 부문, 사용자, 회사, 사업, 사업 관계사, 이슈, **추적 업무**, 변경 이력
- 영업 단계·사업 상태 관리
- 토폴로지 대시보드 (내 보기 / 팀 전체 보기), 상세 패널, 최소 입력 폼
- 알림: 뉴스 티커 + 종 아이콘

### 1.4 후속 단계 (A 로드맵)
| 단계 | 범위 |
|---|---|
| A2 | 대시보드 요약 카드: 단계별 사업 수, 예상 계약월별 금액, 업무 유형별 확인 필요 건수, 담당자별 진행 사업 |
| A3 | 자료: 공유 저장소 **링크 등록** 먼저 → 이후 직접 업로드(Supabase Storage) |
| A4 | 영업기회 1~2장 페이지, 업로드 파일 AI 분석으로 초안 작성 |
| A5 | Outlook: **사용자가 선택한 메일 공유** 먼저 → 자동 분류는 M365 권한 확인 후 |
| A6 | 품목·견적 버전·손익(GP)·분할 빌링·종결 조건, 품의 참조, 유지보수 갱신 사업 연결, Excel 가져오기 |
| 후속 | Microsoft 365 로그인(SSO) 추가, 사내 그룹웨어·더존 iU 연동 |

A6의 핵심 규칙(참고용, A1에서 구현하지 않음): 금액은 공급가액(부가세 별도), 매입은 모든 비용 포함, GP = 매출 − 매입, 합산 이익률 = 전체 GP ÷ 전체 매출, 모든 매출 계산서 발행·매입 계산서 수취 완료 시에만 종결.

- 삭제는 **복구 가능한 소프트 삭제**(`deleted_at`). 연결된 과거 기록을 연쇄 삭제하지 않는다.

- 날짜 판정은 **Asia/Seoul** 기준.
- 수정 요청은 `updated_at` 을 함께 보내 충돌을 감지한다(§8).

### 3.3 영업 단계와 사업 상태

**단계 (`stage`)**
`discovery`(발굴) → `quoting`(견적) → `proposal`(제안) → `negotiation`(협상) → `bidding`(입찰) → `won`(수주) → `fulfillment`(이행: 발주·납품·검수) → `billing`(빌링)

- `bidding` 은 `contract_type = competitive` 일 때만 표시. 수의계약은 건너뛴다.
- 단계 변경은 이력에 남기며, 이전 단계로 되돌려도 기존 업무·이력을 지우지 않는다.

**상태 (`status`)** — 단계와 별개
- `active` 진행, `on_hold` 보류, `lost` 실주, `closed` 종결
- `active` 만 **진행 중 사업**이다.
- A1에서는 사용자가 직접 `closed` 로 바꾼다. (빌링 완료 기반 종결 차단은 A6)

**필수 업무**: 단계가 `won` 이상이면 `delivery` 와 `invoice_out` 업무가 각각 하나 이상 있어야 한다(완료·제외 포함). 없거나 미완료인데 `due_date` 가 비어 있으면 **"일정 미등록"** 으로 본다.

### 3.4 권한 (Row Level Security)
- 일반 사용자: **자기 부문의 모든** 회사·사업·관계사·업무·이슈를 조회·생성·수정할 수 있다.
- 소프트 삭제: 사업 담당자 또는 관리자. 복구: 관리자.
- 관리자: 모든 부문 조회·수정, `teams.join_code` 변경, `profiles.is_active` 변경.
- `teams.join_code` 는 클라이언트에서 조회할 수 없다. 가입 코드 검증은 서버에서만 한다.
- 접근 제어는 서버(RLS)에서 적용한다. 화면 숨김에 의존하지 않는다.

## 4. 상태(색상) 규칙

상태는 **저장하지 않고** 조회 시 계산한다. 기준일은 오늘(Asia/Seoul). 설정값: `YELLOW_WINDOW_DAYS = 14`, `GREY_AFTER_DAYS = 180`, `RENEWAL_NOTICE_DAYS = 30` (단일 설정 모듈).

색과 함께 항상 **상태명 + 아이콘 + 건수**를 표시한다.

### 4.1 사업 노드 (`status = active`)
위에서부터 처음 해당하는 상태:

| 상태 | 조건 | 표시 예 |
|---|---|---|
| 🔴 **RED · 이슈** | 열린 이슈 ≥ 1 | "이슈 2" |
| 🟡 **YELLOW · 확인 필요** | 미완료 업무 중 `due_date` 가 14일 이내이거나 지남 / 필수 업무 일정 미등록(§3.3) | "확인 3 · 배송 D-5" |
| 🟢 **GREEN · 정상** | 그 외 | "정상" |

- Green은 **등록된 정보 기준**이다. 필수 업무의 일정이 비어 있으면 Green이 될 수 없다.
- `on_hold` 사업: 회색 점선 + "보류", 상위 노드 색에 반영하지 않음.
- `lost`, `closed` 사업: 기본 숨김. "종료 포함" 토글 시 회색 + "실주/종결".

### 4.2 관계사 노드 (SI·매입처)
해당 사업 안에서 **그 회사와 연결된 업무**(`deal_tasks.company_id`)만으로 위 규칙을 적용한다. 연결 업무가 없으면 GREEN. 사업의 다른 업무 상태가 관련 없는 매입처로 번지지 않게 한다.

### 4.3 고객사 노드
1. 진행 중 사업이 있으면: 그 사업들 중 **가장 심각한 상태** (RED > YELLOW > GREEN)
2. 진행 중 사업이 없고, 소속 사업 전체의 `last_activity_at` 최댓값이 **180일 이상** 지났으면: ⚪ **GREY · 소원**
3. 그 외: 🟢 GREEN

### 4.4 담당자·중심 노드 (팀 전체 보기)
하위 고객사 중 가장 심각한 상태. 모두 GREY면 GREY. 확인 필요 **사업 수·업무 수**를 배지로 요약한다. 집계는 고유 사업·업무 id로 중복을 제거한다.

### 4.5 구현
상태 계산은 순수 함수(`computeTaskState`, `computeDealStatus`, `computePartyStatus`, `computeCompanyStatus`, `computeRollup`)로 만들고 단위 테스트한다. 서버와 클라이언트가 같은 함수를 쓴다.

### 5.1 가입 (최초 1회)
1. `/signup` 에서 부문 코드 입력
2. 서버가 코드 검증 → 맞으면 "DX사업부문으로 가입합니다" 표시, 틀리면 오류 (IP당 분당 5회 제한)
3. ID(영문 소문자·숫자 4~20자, 중복 불가), 이름, 비밀번호(8자 이상, 영문·숫자·특수문자) 입력
4. 해당 부문 `member` 로 생성 → 대시보드로 이동

### 5.2 로그인
- `/login` 에서 ID + 비밀번호
- 내부적으로 `{login_id}@salestology.local` 로 바꿔 Supabase Auth 이메일/비밀번호 로그인 사용 (이메일 인증 끔)
- `is_active = false` 면 로그인 거부, 기존 세션도 다음 요청에서 차단
- 사용자 메뉴에서 비밀번호 변경 (`/settings/password`)
- 인증 모듈은 나중에 Microsoft 365 SSO를 **추가 공급자로** 붙일 수 있게 분리한다.

### 5.3 최초 관리자
- 시드 스크립트가 `sbbae` 를 `admin` 으로 생성 (멱등)
- 초기 비밀번호는 환경변수 `ADMIN_INITIAL_PASSWORD` 에서 읽는다. **저장소에 비밀번호를 커밋하지 않는다.**

### 5.4 관리자 화면 (`/admin`)
- 부문 목록, 가입 코드 변경
- 사용자 목록, 비활성화/재활성화
- 삭제된 사업·회사 목록과 복구

## 6. 메인 화면: 토폴로지 대시보드

### 6.1 레이아웃
```
┌──────────────────────────────────────────────────────────────────────┐
│ SalesTology  [SalesTology|SOS]  [내 보기|팀 전체]  [티커 ▲]  🔍  ⚙필터  🔔3  sbbae▾ │
├────────────────────────────────────────────────────┬─────────────────┤
│                                                    │  상세 패널       │
│            토폴로지 캔버스 (전체 화면)               │ (노드 선택 시)   │
│                                                    │                 │
│ 🔴2 이슈  🟡5 확인필요  🟢12 정상  ⚪3 소원  [+ 새 사업] │                 │
└────────────────────────────────────────────────────┴─────────────────┘
```
- `[SalesTology|SOS]` 는 A·B 영역 전환 탭 (§11).
- 필터: 담당자, 단계, 예상 계약월, 상태(확인 필요만 보기), 종료 포함.
- 범례 항목을 클릭하면 해당 상태 노드만 강조한다.

### 6.2 그래프 구조
| 보기 | 중심 | 궤도 1 | 궤도 2 | 궤도 3 | 궤도 4 | 궤도 5 |
|---|---|---|---|---|---|---|
| 내 보기 | 나 | 고객사 | 사업 | SI / 직접 매입처 | SI 경유 매입처 | — |
| 팀 전체 | 부문 | 팀원 | 고객사 | 사업 | SI / 직접 매입처 | SI 경유 매입처 |

- 내 보기: `owner_id = 나` 인 사업과 그 고객사. 팀 전체: 부문 전체 (관리자는 부문 선택).
- 같은 회사가 여러 위치에 나타나면 **화면상 노드는 따로, 데이터는 같은 회사 기록**을 참조한다. 하나에 마우스를 올리면 같은 회사의 다른 노드도 함께 강조한다.

### 6.3 레이아웃 엔진 (방사형 궤도 + 물리 시뮬레이션)
d3-force에 다음 힘을 조합한다.
1. **궤도 힘** (`forceRadial`): 깊이 d 노드를 반지름 `R(d)` 원으로 당김
2. **각도 힘**: 노드를 자기 **부채꼴 영역**의 목표 각도로 당김. 부채꼴 크기는 서브트리의 보이는 리프 수에 비례하고, 펼치기·접기 때 다시 계산
3. **연결 힘** (`forceLink`): 부모-자식 거리 유지
4. **충돌 힘** (`forceCollide`): 노드 크기 기반 겹침 방지

동작:
- **유휴 움직임**: 낮은 alpha 유지 + 노드별 작은 흔들림으로 천천히 떠다님. `prefers-reduced-motion` 이면 끔.
- **펼치기/접기**: 노드 클릭 시 토글. 자식이 부모에서 퍼져 나오고, 접을 때 부모로 모인다.
- **초기 상태**: 고객사·사업까지 펼침, SI·매입처는 사업을 클릭해야 펼침.
- **드래그**: 놓으면 탄성 있게 제자리로 복귀.
- **줌/팬**: 줌 0.5 미만이면 라벨을 숨기고 점·색만 표시.
- **검색**: 회사명·사업명 → 경로를 펼치고 노드로 이동·확대·강조.
- 한 노드의 자식이 30개를 넘으면 상위 30개(상태 심각도·기한 순)만 보이고 "+N개 더" 노드로 추가 펼침.

목표: 노드 500개에서 부드럽게 동작. 넘으면 Canvas 렌더링 전환 검토(후속).

### 6.4 노드 시각 표현
| 노드 | 모양 | 표시 |
|---|---|---|
| 나 / 부문 | 큰 원 | 이름 |
| 팀원 | 중간 원 | 이름 + 확인 필요 배지 |
| 고객사 | 원, 진행 중 사업 금액 합에 따라 크기 증가(로그 스케일, 최소·최대 제한) | 회사명 + 배지 |
| 사업 | 둥근 사각형 | 사업명 + 단계 + 상태명/건수 |
| SI / 매입처 | 작은 알약 | 회사명 + `SI` / `매입` 라벨 |

| 상태 | 표현 |
|---|---|
| RED | 빨간 테두리 + 은은한 발광 + ⚠ 아이콘 + 이슈 수 |
| YELLOW | 노란 테두리 1.5초 주기 깜빡임 + ⏰ 아이콘 + 가장 급한 사유("배송 D-5", "계산서 +2일", "일정 미등록") |
| GREEN | 초록 테두리 + ✓ |
| GREY | 회색, 불투명도 낮춤 + 💤 |

연결선 색은 자식 노드 상태를 따른다.

### 6.5 상세 패널
- **사업 노드**
  - 기본 정보, 단계·상태 변경
  - **확인 필요 목록**: 사유, 관련 거래처, 담당자, 요청일·기한, 다음 할 일. 기한순 정렬
  - 업무 목록: 추가, 완료 처리, 일정 변경, 사유 있는 제외
  - 이슈 목록: 등록·해결
  - 관계사 관리 (SI·매입처 추가, 매입처의 SI 경유 지정)
  - 변경 이력, 수정, 삭제
- **고객사 노드**: 진행 중 사업 목록(상태 포함), 마지막 활동일, 메모
- **SI·매입처 노드**: 이 사업에서 해당 회사와 연결된 업무, 이 회사가 관련된 다른 사업 목록
- **팀원 노드**: 담당 사업 중 확인 필요 목록

### 6.6 입력 폼 — [+ 새 사업]
5분 안에 입력할 수 있도록 최소 필드만 둔다.

필드: 사업명*, 고객사*, 계약 방식*, SI(복수), 매입처(복수), 사업 규모, 예상 계약월, 계약 기간, 물품 요약, 단계(기본 `discovery`), **빠른 일정**: 계약 예정일 · 배송일 · 계산서 발행일

- 빠른 일정에 날짜를 넣으면 각각 `contract` · `delivery` · `invoice_out` 업무가 자동으로 만들어진다.
- 회사 필드는 부문 내 자동완성. 없으면 새로 만들고, 비슷한 이름이 있으면 중복 경고.
- 생성·수정, 업무·이슈 변경 시 `deals.last_activity_at` 갱신.

### 6.7 빈 상태
사업이 없으면 중심 노드만 보이고 "첫 사업을 등록해 보세요" 안내와 [+ 새 사업] 버튼.

## 7. 알림: 뉴스 티커 + 종

### 7.1 알림 생성 (데이터에서 자동 계산)
진행 중 사업·업무·고객사를 기준으로 만든다.

| 종류 | 조건 | 예시 | 긴급도 |
|---|---|---|---|
| `issue` | 열린 이슈 | "F카드 · 망분리 — 이슈 '납기 지연' 미해결 3일째" | 100 |
| `task_overdue` | 미완료 업무 기한 지남 | "D시스템 · 스토리지 — **계산서 발행 필수** (2일 지남)" | 90 (계산서), 85 (그 외) |
| `missing_schedule` | 필수 업무 일정 미등록 | "A은행 · 서버 구축 — 납품 일정 미등록" | 60 |
| `task_soon` | 미완료 업무 기한 14일 이내 | "A은행 · 서버 구축 — 배송 D-3" / "견적 회신 D-1" | 70 − 남은 일수 |
| `renewal_soon` | `period_end` 30일 이내 (종결 사업 포함) | "B공사 · 유지보수 — 계약 종료 D-25, 갱신 확인" | 55 − 남은 일수/2 |
| `going_grey` | 진행 중 사업 없고 마지막 활동 후 150~179일 | "E공사 — 마지막 활동 후 170일, 곧 소원 전환" | 20 |

- 알림 키 = `{종류}:{대상 id}:{기준일}`. 날짜가 바뀌면 새 알림.
- 범위: 내 보기는 내 사업(+ 내가 담당자인 업무), 팀 전체는 부문 전체.
- 생성 로직은 순수 함수 `buildNotifications` 로 만들어 단위 테스트한다.

### 7.2 뉴스 티커
- 상단 바 한 줄, **5초마다** 위로 슬라이드.
- 순서: **긴급도 가중 무작위**, 직전 3개 제외.
- 마우스를 올리면 멈춤. 클릭하면 해당 노드로 이동·확대·강조하고 상세 패널을 연다.
- 알림이 없으면 "✅ 모든 사업이 순조롭습니다".

### 7.3 종 아이콘
- 확인하지 않은 알림 수 배지. 클릭하면 긴급도 순 목록.
- 항목 클릭 = 노드로 이동 + 읽음 처리. "모두 읽음" 버튼.
- **읽음은 알림만 끈다. 사업 색은 업무를 처리해야 바뀐다.**

### 7.4 실시간 반영
- Supabase Realtime으로 `deals`, `deal_tasks`, `issues`, `deal_parties`, `companies` 변경을 구독해 맵·티커·종을 새로고침 없이 갱신한다.
- 자정(Asia/Seoul)에 상태와 알림을 다시 계산한다.

## 8. 오류 처리
- 네트워크·DB 오류: 토스트로 알리고 입력값 유지. 맵은 마지막 정상 데이터를 계속 표시.
- 실시간 연결 끊김: "실시간 연결 끊김 — 재연결 중" 표시, 재연결 후 전체 재조회.
- **동시 수정**: 저장 시 `updated_at` 이 다르면 덮어쓰지 않고 "다른 사람이 먼저 수정했습니다"와 새 값을 보여준 뒤 다시 적용할지 묻는다.
- 권한 오류: "권한이 없습니다" 안내, 대시보드로 이동.
- 폼 검증: 필수값, 날짜 형식, 금액 숫자, 종료일 ≥ 시작일, 회사 중복 경고 — 클라이언트·서버 양쪽.
- 가입: 잘못된 부문 코드, 중복 ID, 약한 비밀번호는 해당 필드에 구체적인 메시지.
- 비밀정보(서비스 키 등)는 클라이언트에 노출하지 않고 로그에 남기지 않는다.

## 9. 테스트

**단위 (Vitest)**
- 업무 상태(완료·제외·미완료), 필수 업무 일정 미등록 판정
- 사업 상태: 우선순위, 14일 경계(D-14 / D-15), 기한 경과, 보류·실주·종결 제외
- 관계사 상태: 관련 없는 매입처로 번지지 않음
- 고객사 상태: 180일 경계, 진행 중 사업 유무
- 롤업: 중복 회사·사업 id 제거
- `buildNotifications`: 종류별 조건, 긴급도, 키
- 티커 가중 선택: 직전 3개 제외, 가중치 비율
- 그래프 변환(DB 행 → 노드/링크, SI 경유/직접 매입처), 부채꼴 각도 계산

**DB**
- RLS: 다른 부문 접근 차단, 관리자 전체 접근, 비활성 사용자 차단
- 이력: 변경과 이력이 같은 트랜잭션으로 기록

**E2E (Playwright)**
1. 가입(코드 → 계정) → 로그인 → 새 사업 등록(빠른 일정 포함) → 맵에 노드 표시
2. 이슈 등록 → RED → 해결 → 원래 색
3. 계산서 업무 기한 경과 → YELLOW + 티커 표시 → 티커 클릭 → 노드 포커스 → 완료 처리 → GREEN
4. 수주 단계인데 납품 일정 없음 → "일정 미등록" YELLOW
5. SI 없는 사업의 직접 매입처, SI 경유 매입처가 올바른 궤도에 표시
6. 두 브라우저에서 같은 사업 동시 수정 → 충돌 안내

## 11. A·B 공동 작업 규칙

### 11.1 폴더 경계
```
src/
  app/
    (auth)/            login, signup, settings      ← A
    (core)/            dashboard, admin             ← A
    sos/               SOS 화면 전체                  ← B
  features/
    topology/          그래프·레이아웃·노드          ← A
    notifications/     티커·종·buildNotifications   ← A
    deals/             사업·업무·이슈·관계사         ← A
    sos/               SOS 로직 전체                  ← B
  shared/              Supabase 클라이언트, 인증 헬퍼, 공용 UI, 타입  ← 공동 (§11.3)
supabase/
  migrations/          타임스탬프_영역_설명.sql (예: 20261021093000_a_deals.sql, 20261022100000_b_signals.sql)
  seed/
docs/superpowers/
  specs/  plans/       A·B 각자 문서
.github/
  CODEOWNERS           A 폴더 → SB, B 폴더 → DJ, shared/·migrations → 둘 다 리뷰
  workflows/           CI(타입체크·린트·테스트), 마이그레이션 자동 적용
```

### 11.2 DB 경계
- 공용 테이블(A 소유): `teams`, `profiles`, `companies`. B는 **읽기와 참조(FK)** 만 하고, 컬럼 변경이 필요하면 A에 PR로 요청한다.
- B 전용 테이블은 `sos_` 접두사 (예: `sos_signals`). A는 건드리지 않는다.
- 마이그레이션 파일명에 타임스탬프와 영역(`a`/`b`)을 넣어 동시에 만들어도 충돌하지 않게 한다.
- B가 SalesTology 사업으로 넘기는 시점(예: 시그널 → 사업 생성)은 A의 `deals` 생성 API를 호출한다. 직접 INSERT 하지 않는다.
- B의 시그널을 티커·종에 띄우고 싶으면 `features/notifications` 에 알림 공급자 인터페이스(`NotificationProvider`)를 두고 B가 구현해 등록한다.

### 11.3 브랜치·PR
- `main` 은 보호: 직접 push 금지, PR + CI 통과 + 상대 1명 리뷰(공용 영역 변경 시) 필요.
- 브랜치 이름: `a/기능명`, `b/기능명`.
- **공통 기반(폴더 구조, shared/, 공용 테이블, 인증)은 A가 먼저 main에 올린 뒤** B가 시작한다.
- `shared/` 변경은 작은 PR로 따로 올리고 바로 합친다. 각자 작업 브랜치는 매일 `main` 을 받아 최신 상태를 유지한다.
- main에 합쳐지면 Vercel이 자동 배포하고, GitHub Actions가 새 마이그레이션을 Supabase에 적용한다. PR마다 Vercel 미리보기 주소가 생긴다.
