## 1. 목적과 성공 기준

### 1.1 목적
웹에서 공개된 데이터(공공 조달, 채용공고, 뉴스)를 모아 **유니포인트가 팔 수 있는 영업기회를 자동으로 찾아내고**, 영업사원이 검토한 뒤 **SalesTology 사업으로 넘기게** 한다. [DJ]

영감: 데모데이 블로그 "잠재 고객 채용공고가 B2B 영업 기회인 이유". 고객이 공개한 정보(채용·공고)는 필요·예산·시점을 담은 구매 신호이며, 신선할 때 접근해야 한다.

### 1.2 범위
- **포함:** 신규 고객 발굴(조달·채용 시그널) + **기존·신규 고객 대상 이슈 기반 제안**(뉴스 키워드 시그널). [DJ]
- **끝점:** "기회를 찾아 사업으로 넘기는 것"까지. [DJ]
- **하지 않는 것 (non-goals):** 고객 연락(메일 초안·발송), 연락처 수집, 링크드인·원티드·잡코리아 크롤링(공식 API 없음·약관 위반), 유료 데이터 구매, 정해진 시간 자동 수집.
- **실패로 보는 것 (anti-goals):** 하루 수백 건이 쏟아져 아무도 안 보는 목록. 근거 없이 AI가 지어낸 숫자. 무료라던 운영에서 과금 발생.

### 1.3 성공 기준
1. 부문 멤버가 [수집 시작]을 누르면 수집 → 분석 → 결과가 끝나고 진행 상황이 화면에 보인다.
2. 결과 리드는 부문 관심 키워드에 맞는 것만 나오고, 점수순 상위 카드만 봐도 쓸 만하다(제외 키워드로 잡음을 줄일 수 있다).
3. 리드 카드 맨 위 한두 문장만 읽고 **어떤 영업기회인지** 안다. 숫자는 원본과 정확히 일치한다.
4. 같은 사업은 발주계획 → 사전규격 → 입찰공고로 진행돼도 **카드 하나**로 이어진다.
5. 리드를 [사업으로 전환]하면 SalesTology 토폴로지에 사업이 생긴다.
6. 사전규격 의견 마감이 다가오면 SalesTology 티커·종에 뜬다.
7. 다른 부문의 키워드·리드는 보이지 않는다.
8. 외부 유료 과금 없이 운영된다.

## 2. 시그널의 종류와 출처

### 2.1 데이터 출처 [DJ]
| 묶음 | API | 용도 | 단계 |
|---|---|---|---|
| 조달 | 나라장터 **발주계획현황서비스** (핵심) | 가장 이른 신호. 예산·발주 시기 | S1 |
| 조달 | 나라장터 **사전규격정보서비스** (핵심) | 사업명·배정예산·규격서·**의견 마감** | S1 |
| 조달 | 나라장터 입찰공고정보서비스 | 공고·기초금액·마감 | S1 |
| 조달 | 나라장터 계약과정통합공개서비스 | 발주계획번호·사전규격번호·공고번호로 **한 사업의 흐름을 묶음** | S1 |
| 조달 | 나라장터 낙찰정보서비스 | 낙찰자(경쟁사), 유찰·재입찰 | S2 |
| 조달 | 계약정보(공공데이터개방표준서비스) | 계약 기간 → **재발주 예측** | S2 |
| 채용 | 사람인 Open API | 기관 시그널 (인프라·보안 등 직군 채용) | S2 |
| 채용 | 고용24 API | 기관 시그널 (공공기관 포함) | S2 |
| 뉴스 | 네이버 검색 API (뉴스) | 키워드(이슈) 시그널, 일부 기관 시그널 | S3 |

모든 인증키는 서버 전용 비밀값. 모두 무료이며 일일 호출 한도가 있다. 조달 API는 `type=json` 으로 받는다.

- 조달 업무구분은 **물품 + 용역**만 받는다. 공사·외자는 받지 않는다. [DJ]
- 운영 플랜은 Vercel·Supabase **무료 플랜** 기준. [제안]
- 조달 원본은 키워드와 무관하게 해당 기간의 물품·용역을 **전부** 받는다(페이지당 최대 건수로). 키워드별 검색 호출은 하지 않는다 — 키워드 수만큼 호출이 늘고 [재분석]이 불가능해진다. [제안]

**구현 첫 단계에서 실제 호출로 확인할 것** (문서·검색으로 확신할 수 없었던 부분):
- 출처별 하루 건수와 일일 호출 한도(개발계정은 보통 1,000회 수준) → 첫 실행 30일치가 한도 안에 드는지. 넘으면 첫 실행 기간을 줄인다.
- 계약과정통합공개 API가 발주계획 → 사전규격 → 입찰공고를 번호로 실제로 이어 주는지, 목록 조회로 되는지 건별 조회만 되는지(건별이면 키워드에 맞은 건에만 호출).
- 입찰공고정보서비스 메타데이터에 "데이터 기간 2025년 1월까지"로 표기된 곳이 있음 → 최신 공고가 실제로 나오는지.
- 사전규격 응답에 의견 마감일시 필드가 있는지, 발주 시기·수요기관 코드 필드 이름.
- 공공데이터개방표준서비스 계약정보는 응답 지연으로 조회 기간이 1주일로 제한됨.
- 사람인 API는 승인이 필요함.

### 2.2 시그널 분류 [DJ]

## 3. 처리 흐름

### 3.1 [수집 시작] [DJ]
부문 멤버 누구나 누를 수 있다. 누르면 한 번의 **실행(run)** 이 만들어지고 수집 → 분석 → 결과 도출이 이어진다.

- 수집 범위 [제안]: 지난 실행 이후 ~ 오늘. 부문의 첫 실행은 최근 30일.
- 같은 부문에서 실행 중이면 버튼을 잠근다. 15분 넘게 진행이 없으면 실패로 보고 잠금을 푼다 [제안].
- 화면에 출처별 진행(대기/진행/완료/실패, 건수)을 보여준다.
- **실행 방식** [제안]: Vercel 함수 시간 제한 때문에 실행을 작은 단계(출처 × 페이지)로 나눈다. 각 단계는 한 번의 서버 호출로 60초 안에 끝난다. 화면이 다음 단계를 차례로 호출하며, 탭을 닫으면 멈추고 다시 열면 이어서 한다. [빌더] 같은 효과의 다른 방식(예: Next `after()`)도 가능.

### 3.2 수집 원본은 공용 [제안]
조달 공고·채용·기사 원본은 부문과 무관하므로 **공용 저장소(`sos_raw_items`)에 한 번만** 저장한다. 출처별 고유 번호로 중복을 막는다. 다른 부문이 같은 기간을 이미 받았으면 그 원본을 재사용해 API 한도를 아낀다.

용량을 아끼기 위해 모든 원본은 핵심 칸(제목·기관·예산·마감·링크 등)만 저장하고, 원본 응답 전체(`payload`)는 **어느 부문 키워드에든 맞은 건만** 저장한다. 나중에 [재분석]으로 새로 맞게 된 건은 핵심 칸으로 리드를 만들고, 상세가 필요하면 그때 다시 조회한다. [제안]

### 3.3 분석 (부문별)
1. **걸러내기**: 부문 키워드로 원본을 거른다(§2.3).
2. **묶기**
   - 사업 흐름: 계약과정통합공개 API의 번호(발주계획번호·사전규격번호·공고번호)로 같은 사업을 묶어 `chain_key` 하나로 만든다. 기존 리드가 있으면 새 카드 대신 그 리드의 단계를 올린다. [제안]
   - 번호로 이어지지 않을 때: 기관·사업명이 비슷하다는 이유로 **자동으로 합치지 않는다.** 카드를 따로 두고, 같은 기관에 사업명이 비슷한 리드가 있으면 "같은 사업일 수 있음 → [합치기]"를 띄운다. 합치면 한쪽 리드에 `merged_into_id` 를 남기고 시그널을 옮긴다. [제안] [빌더] 유사도 기준.
   - 기관: 조달은 수요기관 코드 기준. 채용·뉴스는 이름 표준화(㈜·주식회사·(주)·공백 제거 + 별칭표)로 `sos_orgs` 에 맞춘다. 정확히 맞지 않으면 붙이지 않고 "기관 확인 필요"로 남겨 사람이 고른다. [제안]
   - 기존 고객: 부문 `companies.name` 과 표준화 이름이 같으면 "기존 고객"으로 표시.
3. **점수** (0~100) [제안 — 초기값, 실제 데이터를 보고 DJ가 조정]
   - 적합도: 핵심 키워드 일치당 +3, 확장 +1 (상한 9)
   - 시점: 다음 마감 7일 이내 +3, 14일 이내 +2. 발주 예정이 이번·다음 분기 +2
   - 단계: 발주계획·사전규격 +2 (일찍 들어갈 수 있음), 입찰공고 +0
   - 예산: 1억 이상 +1, 5억 이상 +2
   - 겹침: 같은 기관의 최근 90일 기관 시그널 1건당 +2 (상한 +4)
   - 합계를 최댓값 기준 0~100으로 환산. [빌더] 정확한 환산식.
4. **이미 결정된 리드 갱신 규칙** [DJ: 제안대로]
   - `dismissed`(관심 없음): 새 단계·새 마감이 와도 **숨긴 채** 둔다. 근거 시그널만 쌓는다.
   - `on_hold`(보류): 상태는 유지하고 `has_new_progress` 를 켜 **"새 진행" 표시와 함께 목록 위로** 올린다. 사람이 열어 보면 꺼진다.
   - 그 외(`new`·`reviewing`): 단계·마감·점수를 갱신한다.
   - 키워드 변경·재분석으로 **더는 맞지 않게 된 리드**: 사람이 손대지 않았으면(`touched_at` 없음) 숨긴다. 손댄 리드는 `keyword_mismatch` 를 켜고 "키워드 불일치" 표시로 남긴다. 제외 키워드에 걸린 경우도 같다.
5. **요약** (§3.4)
6. **이슈 감지** (S3) [제안]: 키워드 × 업종별로 최근 7일 기사 수를 직전 4주 주평균과 비교. 3배 이상이고 10건 이상이면 이슈 시그널. 같은 기사는 제목 유사도로 하나로 묶는다.

### 3.4 요약 문장 [DJ: 규칙·템플릿 + Gemini 무료]
- 기본은 **템플릿**. 예: "{기관}이 {발주시기}에 {사업명}을 발주할 예정입니다. 예산 {금액}, {마감종류} D-{n}. 일치 키워드: {키워드}. 같은 기관 시그널 {n}건."
- 점수 상위 **5건**(부문 설정)과 이슈 시그널만 **Google Gemini API 무료 등급**으로 다듬는다. [DJ]
- Gemini에는 수집된 사실만 넘기고 "주어진 사실 밖의 내용 금지"로 지시한다. **예산·날짜 같은 숫자는 카드의 숫자 칸에서 원본 그대로** 보여준다. [제안]
- 한도 초과·오류 시 템플릿으로 대체하고 카드에 "기본 요약" 표시. 실행은 멈추지 않는다.
- 요약 생성은 "요약기" 인터페이스 하나로 감싸, 나중에 유료 모델로 바꿀 수 있게 한다.
- 무료 등급은 입력이 Google 서비스 개선에 쓰일 수 있다. 입력은 공개 데이터라 감수한다. [DJ 수용]
- [빌더] 모델 이름은 구현 시점의 무료 등급 모델 중 고른다. 의존성 추가 없이 REST `fetch` 로 호출한다(공용 `package.json` 변경 회피).

### 4.3 보관 규칙 [DJ, 해석은 제안]
- 실행 기록은 **최근 14일 것은 모두** 보관. 14일 안에 3회 미만이면 날짜와 무관하게 **최근 3회분**은 남긴다.
- 정리 대상: 보관 범위를 벗어난 실행, 그 실행에만 걸려 있고 `touched_at` 이 없는 리드·시그널, **수집한 지 14일이 지났고** 어떤 남은 리드·시그널도 참조하지 않는 원본.
- 키워드에 맞지 않은 원본도 14일은 남겨 둔다. [재분석]과 부문 간 원본 재사용이 그 기간 안에서 동작한다. [제안]
- **사람이 손댄 리드(`touched_at`)는 지우지 않는다.**
- 정리는 [수집 시작] 직전에 같이 돈다 [제안].

## 6. A 영역과의 연동

### 6.1 리드 → 사업 전환
- [사업으로 전환] → B 서버가 **A의 deals 생성 API를 호출**한다. 직접 INSERT 하지 않는다.
- 미리 채우는 값: 사업명 = 리드 title, 고객사 = 기존 고객이면 company_id, 아니면 기관명으로 새 회사, 사업 규모 = budget, 예상 계약월 = expected_order_month, 계약 방식 = 조달 입찰이면 `competitive`, 단계 `discovery`, 담당자 = 리드 담당자(없으면 누른 사람). 사용자가 확인·수정 후 저장 [제안].
- 성공하면 리드 `status = converted`, `converted_deal_id` 저장, 토폴로지의 그 사업으로 가는 링크 표시.
- 같은 리드를 두 번 전환하지 않도록 리드 id를 멱등 키로 보낸다.
- A API가 준비되기 전에는 버튼을 비활성화하고 "준비 중" 표시.

### 6.2 티커·종 알림 [DJ: 사전규격 의견 마감 임박]
- B가 A의 `NotificationProvider` 를 구현해 등록한다.
- 종류 `sos_prespec_deadline`: 단계가 사전규격이고 상태가 `dismissed`·`on_hold`·`converted` 가 아닌 리드, 의견 마감 **D-{prespec_alert_days}(기본 3)부터 마감일까지**.
- 범위: 내 보기 = 내가 담당인 리드, 팀 전체 = 부문 전체 리드.
- 문구: "[SOS] {기관} · {사업명} — 사전규격 의견 마감 D-{n} (예산 {금액})"
- 긴급도: `70 − 남은 일수` (A의 `task_soon` 과 같은 척도). 키: `sos_prespec_deadline:{lead_id}:{기준일}`.
- 클릭: `/sos?lead={id}` 로 이동해 카드를 연다.

## 7. 오류 처리
- 출처 하나가 실패해도 나머지는 계속. 실행 상태 `partial`, 카드·기록에 "○○ 수집 실패(사유)" 표시. 다음 실행이 실패 구간을 다시 받는다.
- 일일 한도 초과: 해당 출처 중단 + 안내, 받은 데이터로 분석 진행.
- Gemini 한도·오류: 템플릿 대체(§3.4).
- 실행 잠금: 진행 없는 15분 후 자동 해제.
- 원본 필드 누락(예산·마감 없음): 칸을 "미공개"로 두고 점수에서 해당 항목만 0.
- 동시 수정(담당·상태·메모): A와 같은 방식으로 `updated_at` 비교, 다르면 덮어쓰지 않고 알림.
- 인증키·비밀값은 클라이언트로 보내지 않고 로그에 남기지 않는다.
